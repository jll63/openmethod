
# BOOST_OPENMETHOD_EXPORT_REGISTRY

Exports the state of a custom registry from the module that owns it.

## Synopsis

[source,c++]
----
BOOST_OPENMETHOD_EXPORT_REGISTRY(registry);
----

Used at namespace scope, after the registry's definition, in _exactly one_
translation unit of the module (executable or shared library) that owns the
registry. It must be placed in a `.cpp` file, never in a header.

## Description

All of a registry's mutable state lives in a single variable (see
cpp:registry_state[]). For a program and its shared libraries to contribute
classes, methods and overriders to the same registry, that variable must be
shared across the modules: the _owning_ module exports it, and every _client_
module imports it with
xref:BOOST_OPENMETHOD_IMPORT_REGISTRY.adoc[BOOST_OPENMETHOD_IMPORT_REGISTRY].

`BOOST_OPENMETHOD_EXPORT_REGISTRY` emits an explicit instantiation _definition_
of the registry state, decorated with `BOOST_SYMBOL_EXPORT`:
`__declspec(dllexport)` on Windows, default visibility on ELF platforms. The
same macro pair works on all platforms.

Unlike
xref:BOOST_OPENMETHOD_EXPORT_DEFAULT_REGISTRY.adoc[BOOST_OPENMETHOD_EXPORT_DEFAULT_REGISTRY]
and the `INDIRECT` pair - tokens defined _before_ including the registry
header, and tied to the predefined cpp:default_registry[] and
cpp:indirect_registry[] - `BOOST_OPENMETHOD_EXPORT_REGISTRY` takes the registry
type as an argument and is written _after_ the registry's definition. It is the
tool for sharing user-defined registries:

[source,c++]
----
// registry.cpp - exactly one translation unit of the owning module
#define MY_MODULE_OWNS_REGISTRY
#include "my_registry.hpp"

BOOST_OPENMETHOD_EXPORT_REGISTRY(my_registry);
----

WARNING: An explicit instantiation definition may appear only once in the
program, so this macro belongs in a `.cpp` file and must not be placed in a
header: every translation unit of the owning module that included that header
would emit one. Within a single translation unit that is a hard error; across
translation units it is ill-formed, no diagnostic required - some toolchains
merge the duplicates quietly, others fail to link. A header carrying the
export therefore appears to work right up until the owning module gains a
second translation unit.

### Multiple translation units in the owning module

The macro expands to an explicit instantiation _definition_, so prefixing it
with `extern` turns it into a _declaration_:

[source,c++]
----
// my_registry.hpp - every translation unit of the owning module
extern BOOST_OPENMETHOD_EXPORT_REGISTRY(my_registry);
----

Like the import side this suppresses implicit instantiation, and it also pins
the symbol to default visibility (`__declspec(dllexport)` on Windows). It is
required as soon as the owning module has more than one translation unit: every
one of them takes the `extern` form, and exactly one `.cpp` additionally emits
the plain form. A module with a single translation unit needs only the plain
form.

IMPORTANT: omitting the `extern` declaration in a multi-translation-unit owning
module produces a module that appears to build but does not export the state. A
translation unit of the owner that neither exports nor declares the export
instantiates the state implicitly; under `-fvisibility=hidden` that copy is
module-local, and because ELF merges COMDATs at the _most restrictive_
visibility, the merged symbol becomes local. Clients then fail to link with an
undefined reference to `registry_state<...>::st`.

Translation units of _client_ modules use
xref:BOOST_OPENMETHOD_IMPORT_REGISTRY.adoc[BOOST_OPENMETHOD_IMPORT_REGISTRY],
which is an `extern template` declaration and may safely live in a header.

On ELF platforms, the pair can be omitted altogether if the program is not
built with hidden visibility. Under `-fvisibility=hidden`, it is required, as
on Windows.

See xref:shared_libraries.adoc[Shared Libraries] for a full discussion,
including the required link setup.
