
# BOOST_OPENMETHOD_IMPORT_REGISTRY

Imports a registry's state from the module that owns it.

## Synopsis

[source,c++]
----
BOOST_OPENMETHOD_IMPORT_REGISTRY(registry);
----

Used at namespace scope, after the registry's definition, in every translation
unit of every module that uses the registry without owning it. It already
includes the `extern` - an import is always a declaration - so it may be
repeated, and is normally placed in the header that defines the registry.

## Description

All of a registry's mutable state lives in a single variable (see
cpp:registry_state[]). For a program and its shared libraries to contribute
classes, methods and overriders to the same registry, that variable must be
shared across the modules: the _owning_ module exports it with
xref:BOOST_OPENMETHOD_EXPORT_REGISTRY.adoc[BOOST_OPENMETHOD_EXPORT_REGISTRY],
and every _client_ module imports it.

`BOOST_OPENMETHOD_IMPORT_REGISTRY` emits an `extern template` declaration of
the registry state, decorated with `BOOST_SYMBOL_IMPORT`
(`__declspec(dllimport)` on Windows, nothing on ELF platforms). The
declaration suppresses the client's own instantiation of the state, so the
client references the owner's symbol instead of creating a private copy. The
same macro pair works on all platforms.

It takes the registry as an argument, so the same macro serves the predefined
registries and user-defined ones alike:

[source,c++]
----
// my_registry.hpp
struct my_registry : boost::openmethod::registry</* policies... */> {};

// Every translation unit of the module that owns the state defines
// OWNS_REGISTRY_STATE before including this header; exactly one of them
// emits the matching BOOST_OPENMETHOD_EXPORT_REGISTRY, in a .cpp file.
#ifdef OWNS_REGISTRY_STATE
extern BOOST_OPENMETHOD_EXPORT_REGISTRY(my_registry);
#else
BOOST_OPENMETHOD_IMPORT_REGISTRY(my_registry);
#endif
----

The predefined registries are named the same way:

[source,c++]
----
BOOST_OPENMETHOD_IMPORT_REGISTRY(boost::openmethod::default_registry);
BOOST_OPENMETHOD_IMPORT_REGISTRY(boost::openmethod::indirect_registry);
----

The client module must be linked so that the reference can be resolved: on
Windows and macOS, by linking against the owning module (for an executable, via
its import library, generated with `ENABLE_EXPORTS` in CMake); on ELF
platforms, a dynamically loaded library may also leave the reference for the
dynamic linker to resolve at load time.

See xref:shared_libraries.adoc[Shared Libraries] for a full discussion,
including the required link setup.
